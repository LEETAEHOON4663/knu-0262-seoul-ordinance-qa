# 설계: 필수근거 그래프 RAG (독립 구현)

> **현행 흐름(V8, 449 실측 후)**:
> 1. 질의계획(Pro4)
> 2. BM25 + IA 노드 dense 검색
> 3. 검색 순위 순서의 조 묶음 + 필수근거(1만 자), 상위 근거마다 질문과 가까운 호·목·표행 발췌(focus)
> 4. **근거 선택(Pro4)**
> 5. 선택 근거 + 그 필수근거로 **답변(Pro4)**
> 6. 검증(Mini4) → 지적이 있으면 교정 1회(Pro4). 재검증 기권은 기본 off
> 7. 답변 문장 속 조항 인용 보충(코드) → 조립
>
> - 근거 ID는 `주차장:제18조제2항` 형식입니다. schema 필드는 판단이 결론보다 먼저 나오도록 `a_`/`b_` 순으로 이름을 붙였습니다.
> - 아래 2~3절의 "한 호출로 선택·답변" 설명은 첫 설계입니다.
> - 바꾼 근거와 수치는 [RESULTS_449.md](RESULTS_449.md), [PILOT_RESULTS.md](PILOT_RESULTS.md), [COMPARISON_IA.md](COMPARISON_IA.md)에 있습니다.

## 1. 출발점 (인계 자료 기준)

- 현행 R9 cascade_v1의 흐름: 최초 검색 기준 gate → Pro4 질의계획 → 후보 100→40 → 필수관계 묶음 → Pro4 근거 선택 → Pro4 생성 → Mini4 검토 → Pro4 교정 → Mini4 재검토 → Mini4 정규화.
- R9는 오프라인 358검사만 통과했고, 실제 Solar 점수·지연은 측정하지 않았습니다. R6는 449개 중 111개 처리 후 중단됐습니다(처리분 평균 83.56%).
- 그래프 실제 범위: 원문 525, 세부 target 22, 검토 간선 70. 대부분은 원문 전체 fallback입니다.
- 인계 자료에 기록된 실패:
  - 선택기 입력에 필요한 원문이 있었는데 선택에서 빠졌습니다(A03/A56).
  - 설명문 답변 + 빈 근거 조합의 계약 위반이 있었습니다(A20/A25/A100).
  - 검토 승인 9건 중 8건에 설명형 기권이 남았습니다(R6 실관측).

## 2. 약점 판단과 바꾼 점

| R9 약점 | 이 구현 |
|---|---|
| 선택(B 묶음)과 생성이 다른 호출이라 선택 누락이 생성에서 복구되지 않음 | ③⑤ 한 호출에서 요구 분해 → 요구별 근거·지원 여부 → 답변·사용 근거. 전체 후보 원문이 답변 모델에 그대로 남습니다. |
| 기권을 답변 문장(“확인 불가…”)과 빈 인용 조합으로 판정해 계약 오류·정규화 단계가 필요 | ⑦ 기권은 `requests[].supported=false` 구조 판단으로 정합니다. 그 경우 코드가 정확한 기권 객체를 만들고 답변 문장은 제출하지 않습니다. 정규화 호출과 문구 정규식이 필요 없습니다. |
| 최초 검색 점수 gate가 모델 판단 전에 기권 | ③ 점수 gate 없음. 어휘가 하나도 겹치지 않아 후보가 0개일 때만 모델 없이 기권합니다. |
| 검토 → 교정 → 재검토 → 거부 시 기권. 호출이 많고 과유보 위험 | ④ Mini4 검토 1회 → 지적이 있으면 Pro4 교정 1회로 종료. 교정 모델은 지적이 틀릴 수 있음을 알고 원문으로 재확인합니다. |
| 요청당 chat 호출 최대 약 7회 | 최대 4회(계획·답변·검토·교정) + 공유 계약 복구 1회 |
| 검토에도 전체 후보 전달 | 검토 입력을 사용 근거 + 같은 조/별표 + 그 필수근거로 축소(중앙값 약 1.2천 자) |
| 별표가 셀 좌표 선형화 텍스트(“[셀 행3 열5; 행병합…]”) | ① 병합 셀을 복원한 행 단위 표로 렌더링. 전체 폭 비고 셀은 문단으로 둡니다. 셀 문자열 손실 0건을 검사합니다. |

규칙을 늘리는 대신 작업 단위를 줄였습니다. 프롬프트의 판단 기준은 질문 핵심 요구 / 원문 직접 지원 / 위임·운영사실 / 주체·의무·재량 보존 / 정형 기권, 이 다섯 가지 축으로 정리했습니다.
IA·R9 원문 프롬프트는 복사하지 않았습니다.

## 3. 8항목별 구현

| 번호 | 구현 | 생략·한계 |
|---|---|---|
| ① 문서 준비 | corpus.json 원문 525단위 재사용(라벨=인용 형식). 고정 조례 원문과 전문 대조 0건 불일치. URL·시행일은 ordinances.json 정본. 별표 표 복원. | 그림 서식(별도 3~6)은 남은 부분 텍스트만 있습니다. 명제 단위 재분해는 하지 않았습니다. 세부 target 22개를 따로 쓰지 않는 이유: 전달 단위가 원문 전체라 검색 단위만 달라지기 때문입니다. |
| ② 색인 | 어절 + 문자 bigram BM25. dense는 선택(서버 vectors.json 재사용, 해시 검증). | 형태소 분석기·재임베딩 없음. dense 경로는 합성 벡터로만 검사했습니다. |
| ③ 해석·검색 | Pro4 질의계획(조례 0~2개 + 조문 용어 검색어 1~4개, 원질문 보호). 가중 RRF. 조 단위 확장(2,500자 이하일 때) + 필수근거 1단계. 원문을 자르지 않고, 예산을 넘는 하위 묶음은 통째로 제외. | 질의계획 실패 시 원질문 검색만 사용하며 기록을 남깁니다. 필수근거는 1단계까지만 복원합니다. |
| ④ 근거 검증 | Mini4가 질문·초안·축소 근거를 대조하고 다섯 종류의 지적만 반환. | 검토 실패·시간 부족이면 검토 전 답변을 유지하고, 상태(`unavailable`/`skipped`)를 기록합니다. |
| ⑤ 판단·답변 | 요구별 근거·지원 판단 후 2~4문장. 사용한 모든 근거 E코드. | 법률 내용 정확도는 미측정입니다. |
| ⑥ 인용·출력 | E코드 → 원문 라벨 → citation. URL·시행일은 첫 사용 근거의 조례 메타데이터. 엄격 파서(중복 키, 미지정 ID, 필드 조합). 복구는 실제 오류명과 이전 출력을 함께 보내 1회. | 여러 조례를 함께 인용하면 URL은 첫 근거 조례 하나만 씁니다(계약상 단일 필드). |
| ⑦ 답변 가능 여부 | 지원 안 된 핵심 요구가 하나라도 있으면 정형 기권. 운영 오류는 기권과 분리. | 핵심/배경 구분은 모델 판단입니다. |
| ⑧ 결합 | 수신 시점부터 85초 공통 마감(대기 포함), 단계별 상한, 예산 선예약, 처리 불명 호출은 재전송 금지·예약액 보존, 성공 응답 캐시(replay), 기본 offline. | 공유 원장과 연동하지 않습니다(README 예산 주의 참고). |

## 4. 원문 → 표현 → 전달 추적 (예: 공영주차장 주차요금)

1. **원문**: `unit:2171833:제6조제1항`(“주차요금은 별표 1과 같다”), `unit:2171833:별표1`(HWP 선형화 2,827자).
2. **그래프**:
   - 제6조제1항 → 별표1 (검토 간선 REFERENCE)
   - 별표1 → 제6조제1항 (검토 간선 LEGAL_BASIS)
   - 별표1 비고의 “법 제7조제1항 및 제12조제1항”은 주차장법 조문이므로 조례 조문으로 연결하지 않습니다(테스트로 고정).
3. **표현**: 별표1을 `| 구 분 | 노상주차장 | … |` 행 표 + 비고 문단으로 렌더링합니다.
4. **전달**: 순위 상위 조 묶음과 필수근거를 조례 순서로 정렬한 뒤 E1…En을 부여합니다. 답변 요청 schema의 enum은 이 E코드만 허용합니다.
5. **조립**: 모델의 `evidence_ids` + 지원 요구 근거 → 원문 라벨 → `citation`. 원본 check.py의 `score_citation`으로 자기 라벨이 1점인지 검사합니다.

`python3 -m lawqa context "질문"`은 3~4단계를 API 없이 출력합니다. 실제 실행 기록은 `runtime/traces`에 남습니다.

## 5. 검증 구분

- 오프라인 68개 통과:
  - 자료 무결성: 라벨 525개를 원본 check.py로 파싱, 본문 전문 대조, 표 셀 보존, 메타데이터 일치
  - 그래프 간선과 외부 법령 배제
  - 검색 결정성과 원질문 보호
  - 계약 파서 오류 코드
  - 결합 경로: 정상, 기권, 설명문 기권, 복구 성공·실패, 복구 1회 공유, 교정, 계획 실패, 시간 초과 재전송 금지, 예산, 캐시 재생, 마감 공유
  - HTTP 계약
  - 채점 도구의 원본 규칙 일치
- 실제 모델 성능: 측정하지 않았습니다. 가짜 transport의 성공을 Solar 성공으로 부르지 않습니다.
- 알려진 위험:
  - 요구 분해 단계에서 모델이 부수 요구를 핵심으로 잡으면 과유보가 생깁니다.
  - 문맥 1.6만 자에서 Pro4가 근거를 고르는 정확도를 모릅니다.
  - 비용 상한 추정이 잔여 예산을 넘을 수 있습니다(README).
